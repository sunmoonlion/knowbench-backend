## 运行数据与职责

| 入口 | 职责 |
| --- | --- |
| `domain/workbench/execution_plan.py` | 将冻结目录和已接受计划投影成现有 StepContract；只解析实例名、输入连接、covers/back_to 和工具子集，不重编译作者方法 |
| `application/workbench/plan_receipts.py` | 共用的只读收据入口；按 Task 指针读确切计划版本，核任务/作者摘要/规划轮次归属 |
| `application/workbench/execution_plan.py` | 任务局部读取、已验收成果及输入版本核验、当前 Attempt 权限绑定检查 |
| `Ledger.open_method_step` | 持 Task 锁核状态/版本/方向盘/取消，再绑定输入、按作者预留预算并开启现有 Attempt |
| `Ledger.accept_method_plan` | 与派发共用已验收成果读取规则，重规划不能从任意最新 Artifact 推断成果已通过 |
| `application/workbench/method_planner.py` | 用现有 TurnDriver 发普通规划轮次；严格解析提案，经 Ledger 接受，预算、取消和失败均入现有账 |
| `active_method_inputs` / `judge_numbers` | 动态 covers 按活动 Attempt 绑定的输入版本验收；不读同名最新成果 |

同一作者包的多个任务不共用计划。固定专家仍读原有包；动态投影不写入作者包缓存，也不
覆盖 `pack_snapshot` 或 `pack_digest`。未知运行契约、无已接受计划、越权工具均拒绝。

Attempt 的 `step_id` 是本任务的实例 ID；`refs` 记录计划版本/摘要、作者包摘要、方法别名/
版本、实例位置和所选工具。`input_artifact_versions` 保存槽、上游实例、成果名、版本、ID
和摘要。输入中的 future binding 在开步时绑定，已经写明版本的 binding 不会自行跟随新值。
计划快照、作者方法与执行成果分别保留版本，不增加第二套运行状态或计费账。

`accepted_results` 只认游标前的已完成实例，该实例最近一次执行 Attempt 必须成功，再按它登记的输出
ID/版本取原件；不按名称取最新 Artifact。每一项还要核其历史计划、方法身份、工具范围与
输入链。回退游标立即排除后缀；上游返工后，即使错误地推进游标，也不能把依赖旧版本的
旧结果恢复成有效结果。确切 pin 失效时，开步事务先拒绝，Advisor 再发有界规划轮次；
只允许将失效后缀的显式输入版本重新绑定到同一上游已验收新版，形成新计划收据。
已完成前缀、已开始实例的方法/顺序/依赖/权限及旧收据不改，不能临时把 pin 改为 latest。`final_artifacts` 指向计划指定的全部最终实例，不由“最后一轮”猜。

## 并发与取消

Task/Attempt 的写路径统一先锁 Task，再锁 Attempt。`attempt_transition` 只无锁读取
不可变 task_id 来找 Task，状态仍在加锁后核对；取消在 Task 锁内读取当前活动 Attempt。
此前取消先窥读活动 ID，再锁 Task，会漏掉其间新开的轮次，造成任务已取消但预留仍在。
本轮已补确定性并发复现：旧实现残留 0.05，修复后轮次取消且预留归零。开步、取消、
无人推进收尾和迟到费用使用同一顺序，避免一条路径反向加锁。

## 验证与后续接入

规划服务只把作者规划原文、方法选择条件/输入槽/输出形状/允许工具、既有计划及有效成果
版本交给模型。输出采用既有 MethodPlan 严格契约，不能夹带正文、验收或预算；过长的问题
按作者 input_max_chars 截断并显式标记。作者的输入槽和任务实例分开，重规划提示与账房
均保护已开始前缀；失败轮次也消耗作者限定的规划次数。并发调用只发一轮；费用超限不接受
计划；环境断开、超时、中断的进度文字不能当作有效计划。

`run(task_id, parent_version=0)` 是初次规划；调整必须显式携带当前父计划版本。已有计划
时重试初次派发、或重试已经落库的调整均只读返回，不能自动升级为新一轮重规划并收费。

规划结果结算持 Task 锁：完成 Attempt、费用、计划 Artifact/指针/事件、回到 QUEUED 一起
提交。非法提案先整体回滚，再单独结算失败费用并留拒绝原因，下一轮能据此修正；取消后
的迟到响应只补记费用，不接受提案。turn_id 在终态结算时与费用一起登记，避免只登记
RUNNING 的 turn_id 就被误认为已付费。故障回滚后仍由现有 Runner 收尾/恢复，不另建账。

`turn.py` 仅抽出原 Advisor 的 TurnResult/TurnDriver/时限，Advisor 保留旧 TurnResult 导入
入口；没有新增模型客户端。测试中的 Driver 是替身，不能当作真实沙箱规划或生产集成验收。

运行 `tests/test_execution_plan.py`、`tests/test_execution_plan_db.py`、
`tests/test_method_plan.py`、`tests/test_method_plans_db.py`、`tests/test_workbench_ledger_db.py`。
数据库测试使用既有 `AGENT_TEST_DATABASE_URL` 的隔离 schema，包含并发开步、取消竞态、
预算拒绝、事件故障回滚、重复方法、跨任务隔离、重启、旧成果失效及固定专家回归。
合成测试不调用模型、外部证券数据、Wind 或线上任务。

规划与固定输入验收另跑 `tests/test_method_planner_db.py`、
`tests/test_method_acceptance_db.py`、`tests/test_knowbot_compute.py`；覆盖提案修正/重启、
非法工具、已执行前缀改写拒绝、并发规划、预算不足/超限、取消迟到计费去重、跨任务误用、
事件故障整体回滚以及“同名新版本不替换开步输入”的 covers 验收。

## Advisor 执行与原子收尾

Advisor 在无计划时调用 MethodPlanner，随后按任务视图开方法 Attempt；规划和定数据的
完成不算作首个方法已执行，范围检查仍在首个方法进行。每个步骤边界先检查数据等待，
最后一步也不能绕过未确认的补采单直接成功。

验收的远程原文/文件读取不持 Task 锁；结果结算再次核活动 Attempt、计划和绑定。
输出 Artifact、费用/turn_id、成功或失败事件、游标与回队列/返工/交人同一事务提交。
验收服务异常或绑定不符不得收成果，已发生的费用仍结算为平台失败。取消期间返回的
结果仅补费用；旧回执不能撤销新轮次的问题，也不能释放新轮次占用的项目。

最终交付再次检查全部有效前缀及 final_outputs，只用验收收据指向的成果，排除返工旧版。
文件指纹读取后复核 Task 版本/取消；handback、产出 Outbox 与成功终态同事务。
故障回滚后可从已完成游标恢复交付，不再次调用模型。动态 terminal_result_ref 指向包含
全部最终成果引用的 handback，固定专家仍保留原最终成果引用语义。

新增 `tests/test_method_advisor_db.py` 覆盖完整规划/执行/返工/重启/多最终成果、明确钉版
失效后的新计划与次数耗尽、事件故障回滚、验收异常计费、取消期间验收/文件校验、迟到
回执与新轮次交错。另用既有 ScriptedAppServer 驱动真实 Runner 的 WebSocket 协议循环；
这是预录响应工程测试，不是付费真实模型或真实渠道验收。

## 作者测试的稳定期望与多份最终成果

沿用 knowlab 提供的 `knowbot-test-run/v1` 和原有 `equals/approx/contains` 判据。
动态清单的 `expectations[].artifact` 必须是作者在 `planning.final_units` 声明的
方法别名，例如 `report`；不能填任务运行后才生成的 `report_42` 或内部 Artifact 名。
作者端在建测试/签数据授权之前拒绝不匹配的期望，运行方也做相同语义检查。

`final_results` 经当前接受计划的 `final_outputs` 取得确切实例，再按既有已验成果规则
读取 ID/版本/摘要。计划校验已要求最终实例是该方法在计划中的最后一次调用；测试读取
仍核收据，不自行按位置或同名最新 Artifact 猜测。返工后的失效结果不能满足断言。

提供方仅扩展 case-outputs schema：动态回执带 `plan_version` 和 `final_outputs`。
每份保留方法别名、实例 ID、已验成果引用和受大小限制的 JSON；未完成的引用为 null。
有登记文件时通过原有作者工作区读取通道附该文件，读取失败或超时有说明；不再仅取
最后一份文件。成果引用摘要是已验 JSON 的摘要，不能冒充后来读取的文件文字摘要。
步骤的 `current=false` 表示历史尝试仍可查、现已不构成有效成果，不能只看 `accepted`。

每份 JSON/文字和总响应沿用既有上限；超限先去内容并记省略，不去掉最终成果身份。
旧固定专家不发这些可选字段，原单文件路径与响应形状保留。请求、结果及回答 schema
没有新增字段，provider 与消费方只更新产出 schema 摘要，不另造断言引擎或接口版本。
测试：`test_method_test_outputs.py`、`test_method_test_exports_db.py`、既有契约锁及测试
运行回归；真实数据库覆盖多实例、多文件、未验同名新版、返工失效及未规划任务。


## 真实轮次与工具权限

`method_tools.py` 复用现有 Task/Attempt、沙箱身份与会话事件。Runner 发 turn/start 前捕获
活动 Attempt，收到响应后将实际 turn_id 写入 refs.runtime_turn_id；它不等于计费完成，
不会提前写入用于费用去重的 turn_ids。绑定失败要中断并保留实际用量，不能收到响应却
丢掉费用。规划使用宿主只读策略、不挂用户执行环境，不准提权；方法轮次恢复原执行环境。

HTTP MCP 在所有本地工具和数据中继之前检查：

- `_meta.x-codex-turn-metadata` 的线程、轮次与 callId 必须与 Runner 经已认证 app-server
  收到并落库的 item/started 相符，server、tool、完整 arguments 也一致。metadata 本身
  不是凭据，模型给的 task/conversation 更不是。沙箱 JWT、线程所有者及沙箱记录必须对应。
- HTTP 与 websocket 可能先后到达，最多等 2 秒让事件/轮次绑定落库；不锁 Task 等网络，
  超时拒绝，不回退放行。turn/completed 后旧调用不能重放。
- 动态任务只认当前活动 Attempt 及其已接受计划、固定输入和所选工具。规划轮次无工具；
  定数据只许 find_subject/describe_items/request_data；方法按冻结子集。拒绝借另一任务、
  conversation 或 scope=market 绕过；lookup/describe_items 即使不带 task，也必须通过
  该轮次的工具子集检查，再走现有 knowbase 公共发现规则。
- DataRelay 仍向 knowbase 传服务端持有的运行授权。模型不能直接提供底层 run/session；
  方法工具授权不替代数据授权，更不替用户确认采单。动态定数据在 MCP 未配置时失败，
  不把“没有工具”写成“数据齐了”。
- 为防去掉 task 参数或取消后退回旧入口，账户一旦存在动态任务历史，该账户的调用都需
  可核实的执行来源。普通聊天使用原有 turn/accepted（by=user）证明，仍可并行使用自己的
  数据会话；仅有固定专家的账户保持既有路径。不能手工删除历史来规避此检查。

原生审批按活动方法和实际 turn_id 定位，规划/定数据不能借下一方法的权限放行；绑定
损坏、旧轮次或作者明确 deny 都拒绝，已有任务授权和重复请求不能扩大作者边界。该检查
针对 app-server 发来的审批请求；本轮没有另建本机命令执行器或声称屏蔽所有只读宿主工具。
`tools/list` 仍列平台能力，调用时强制限制，不能将清单展示当作每轮的权限凭据。

### 固定版本协议探针

`scripts/probes/codex_mcp_provenance.py` 只在无外网、全新 home 的一次性容器中运行；Responses
和 MCP 都是 loopback 合成服务，不读任何用户 Key、不调用真实模型/Wind。以当前开发基线 Codex 0.170.0 和原基线 0.155.1 分别验证：模型 MCP 调用有线程/轮次/callId，且与 item/started 一致；客户端直接
mcpServer/tool/call 没有轮次身份。thread/start 的 MCP header 可分线程，但已装载线程的
thread/resume 不更新 header，unsubscribe 后再 resume 才更新。因此实现不依靠热重写全局
header，不动其他线程配置。升级 Codex 时须重新跑此探针，不能把版本实测当永久协议保证。

运行方式（准备本地已验证的固定版本二进制及已有含 Python 的镜像；不自动下载）：

```sh
probe_codex_bin=/absolute/path/to/pinned/codex
probe_python_image=your-existing-python-image
docker run --rm --network none --read-only --cap-drop ALL \
  --security-opt no-new-privileges --user 0 --tmpfs /tmp --tmpfs /root \
  -v "$probe_codex_bin:/probe/codex:ro" \
  -v "$PWD/scripts/probes/codex_mcp_provenance.py:/probe/probe.py:ro" \
  --entrypoint python "$probe_python_image" /probe/probe.py
```

探针让同一线程在相同 MCP 配置下连续完成两轮合成工具调用，核对网关只初始化一次，并逐轮比对不同的 turn/call 与宿主事件。输出含版本和各项核验结果。通用接口参考
[官方 app-server 文档](https://developers.openai.com/codex/app-server/)与
[MCP 配置文档](https://developers.openai.com/codex/mcp/)，上面的热更新与 metadata 结论
以固定二进制实测为依据。生产接入前仍需真实沙箱的完整工具轮次验收。

`test_method_tools_db.py` 覆盖伪造元信息/参数、旧轮次、跨沙箱/任务/会话、市场与无范围
入口、取消后省略 task、绑定损坏、并发到达、底层 grant 注入、原生审批与作者 deny。
`test_method_runner_mcp_db.py` 经真实 Runner websocket 读取、真实 MCP HTTP 路由和隔离
PostgreSQL，调用合成 knowbase 并完成计划/方法/最终交付；它仍不代表真实供应商验收。

规划上下文另带最多 100 份已钉资料元信息（名字/来源/原件版本/读法）与 100 条请求编号和状态，超出显式计数；不带 grant、未读取正文或未确认需求内容。它只帮助选择方法，不能作为数据已可读的授权证明。

### 补采并发提交边界

knowbase 的 `resolution_changed` 表示解析期间基版已变，工作台返回明确的
提采错误，要求重读后重试，不伪装为 `listed`。本地收到正常结果后按 Task → resolution
顺序锁定、重读最新 detail，再追加请求；保留远程调用期间写入的预切合等字段，拒绝
重复编号和终态任务的迟到回包。作者测试没有远程清单，编号与追加在同一短事务完成。
取数和远程解析不放进这些行锁事务，既有需要续跑任务的收尾使用同一锁序。

提供方 knowbase 在既有修订锁下校验读取基版，过期追加/修改/刷新回 409，不覆盖赢家。
旧提供方即便同时报成功，本地重复编号也会报错而非覆盖另一请求；但这不能修复旧提供方
已丢失的远程清单，联合验收必须用带基版检查的 knowbase。

尚未覆盖远程追加成功但 HTTP 响应丢失、或本地写入前进程退出的自动恢复；重试可能收到
`need_key_taken`，不能当作成功，也不能绕过本人确认直接取数。当前改动没有引入操作
收据/自动对账，不声称跨服务 exactly-once。用户确认、改采单与新请求同时发生的完整
并发合并也仍需单独验证；此段只保证所列提采提交与 provider 基版冲突的边界。


### 受控动态孵化测试入口（开发分支）

### P3 复核线程的模型路由探针

在后端仓根下使用项目的 Codex 0.170.0 沙箱镜像运行。探针在同一 app-server 开两个线程，分别指定两个合成供应商和模型。用主笔、复核、主笔三个轮次核对启动回参、实际收到请求的服务、请求体中的模型名和用量事件归属。全程使用容器内的回环服务。

```sh
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp:exec -e CODEX_HOME=/tmp/probe-home -e HOME=/tmp \
  -v "$PWD/app/scripts/probes:/probe:ro" --entrypoint python3 \
  luna-local/sandbox:codex-0.170.0 /probe/codex_review_models.py
```

此次用量事件只有线程、轮次和 token 统计。真实供应商身份、模型家族、不同路由的单价、独立工作区和恢复后隔离仍须由产品链路另验。

### 单轮纯指令工具的隔离试跑

对于 Skill，KnowBench 从作者获准的安装读回 `SKILL.md`，核对清单中的字节数和 SHA-256。对于独立登记的指令，KnowBench 按作者、来源 ID、版本和摘要从管理中心读取正文，重新计算 UTF-8 字节的 SHA-256。工程试跑以已有的校验运行号为入口，重新核对作者、服务调用方、定义、安装修订、执行许可及输入槽，只将指令正文、步骤说明及本次输入交给隔离进程。当前样例取独立文本输出，不需要其他工具或文件。

在后端 `app/` 下提供一次性 PostgreSQL 测试库（`AGENT_TEST_DATABASE_URL` 的库名以 `_tests` 结尾），以及项目的本地 `luna-local/sandbox:codex-0.170.0` 镜像，即可复跑。模型供应商和价目均使用本地测试数据。

```sh
RUN_CODEX_INSTRUCTION_PROBE=1 .venv/bin/pytest -q tests/test_formal_instruction_db.py
```

真实 app-server 的四个样例各用新临时线程，容器只读、禁外网，线程没有工作环境、MCP 或动态工具。正常样例对照实际输出槽验收，类型错误的输出被拒。两个提问样例揭示同一线程轮次的不同费用结果。Codex 会把 `request_user_input` 列给模型，在默认模式内部拒绝它，不向宿主发提问请求；一个轮次随后可以再次请求供应商。不设限时一次轮次发了两次请求，两次的用量都进入该线程的累计值。测试供应商在接收下一次请求时限额，则只处理第一次，轮次失败退出，保留第一次用量。四种情况都保持原孵化校验待验。

正式接入要将请求许可绑定到实际供应商、模型和同一 Attempt，按输入量、输出 token 上限及对应价目预留根预算；请求发出前占用次数，并发、重连和恢复共用这份记录。失败也要结算已知用量，计量未知时保留待核状态。宿主另验完整输出及其槽位。此探针的内存计数只适用于断网验收。作者试跑的正式账本和私有冻结见下文。

### 纯指令试跑的一次请求与根预算

工程宿主可以在已经排队的纯指令验证 Task 上开启一次 Attempt。它使用该账号获准的供应商、模型、接入地址、凭据编号和价目。单供应商账号可沿用部署的默认地址。当前采用保守预留，用已核定的模型上下文上界乘以最高输入单价，加上输出上限的费用；账本按供应商实际报告的各类 token 核销。根预算不足时不创建 Attempt。

沙箱转发首个 Responses POST 前，KnowBench 重核当前凭据、指令许可、业务输入与输出契约，限定输出 token 数，在独立提交的事务中占用唯一请求名额。转发器核对目的地址，经一次连接发送，保留终结事件的供应商响应编号与用量。请求已放行而回执尚缺时，失败或取消仍保留预留；同一份迟到回执可重复交回。未识别的计价字段和不完整的 token 合计保持待核。

有同级 `sunmoonun` 仓、断网探针镜像及测试库时，在后端 `app/` 运行下列用例。非并列检出可将 `SANDBOX_INSTRUCTION_RELAY` 指向对应的沙箱源码文件。

```sh
RUN_CODEX_INSTRUCTION_PROBE=1 .venv/bin/pytest -q tests/test_instruction_requests_db.py tests/test_instruction_control_db.py
```

本地联调用只读、无外网的 Codex 0.170.0 容器。容器只交出本次模型请求并收回 SSE 响应。进程外的可信转发器经验证证书的 HTTPS 调 KnowBench 正式路由，独立的回环供应商提供测试响应。数据库为 PostgreSQL。用例同时核对同轮第二次请求、真实轮次编号、用量及取消后的迟到回执。

### 纯指令转发器的控制接口

可信宿主在开启 Attempt 时记录专用转发器的 UID。放行和回执共用 KnowBench 签名的短期专用票据，绑定所有者、根 Task、Attempt、用户沙箱、转发器 UID 和模型凭据编号。转发器从独立挂载的票据文件取令牌，用自身的 UID 和 Attempt 编号请求内网 HTTPS。票据只交付给该 Attempt 的可信转发器。控制路由本身不签发票据。

| 入口 | 何时调用 | 核验与恢复 |
| --- | --- | --- |
| `POST /api/internal/v1/instruction-control/claim` | 发送模型请求前 | 重核票据与持久绑定、实际装载的凭据编号、供应商地址、模型、工作稿及预算。提交唯一名额后返回允许转发的地址和请求体。 |
| `POST /api/internal/v1/instruction-control/receipt` | 收到供应商终结用量后 | 核对原 Attempt、轮次、响应编号和 token 明细，沿用预留时的价目。取消或路由停用后仍能补交原回执。 |

`WORKBENCH_INSTRUCTION_ROUTES` 默认为空。每条运营配置包含 `provider`、`model`、`base_url`、`price_key`、`context_tokens`、`output_tokens`；单供应商只需一条。上下文上界由实际供应商核定。供给器收到凭据编号后，将编号、供应商、模型、接入地址和密钥合成一个 Secret 项供转发器投影，轮换时整项读取。

转发器在自己的回执目录写入本次供应商回执并持久化，再向 KnowBench 提交。若确认丢失，重启后调用 `InstructionControl.reconcile()`，只补发原回执。执行票据可由可信宿主为原绑定续签。回执目录须跨该转发进程重启保留，清理由宿主在确认结算后执行。

### runner 领取与恢复纯指令试跑

已受理的工程试跑由 KnowBench runner 推进。runner 在开 Pod 前核对校验运行、执行许可、本人账号及运营报价，先在根任务上预留一次请求的预算。预算不足进入资源等待。在专用执行容器新建只读 Codex 线程，将容器 UID 和线程号持久写到同一次 Attempt 后才发起轮次。取得真实轮次号并记账后，转发器才能占用供应商请求名额。线程历史只保留在专用执行 Pod 的临时卷。

| 中断位置 | 再次领取时的动作 |
| --- | --- |
| 预留 Pod 的响应丢失 | 按所有者与任务只读查询原预留。已确认未建立连接才可重试创建。供给器明确报告控制源关闭时结束试跑。 |
| 已经发起轮次，缺少轮次号 | 保留原 Attempt，等到十分钟执行期限后交回失败。 |
| 已知轮次，结果尚未入账 | 只读同一执行容器的原线程历史，核对完整轮次、输出契约和原用量回执后交付。 |
| 已有合法输出，原用量回执暂未送达 | 网关先把用量写盘，执行容器可收全本轮输出。runner 保留预留和原轮次，在执行期限内等回执到账后读回结果并结算。 |
| 用户取消，用量待回 | 停执行容器，保留网关、预留预算与回执卷，向原网关续票。账本核销后，先回收实例，再按卷身份回收凭证。原网关丢失且用量未知时保留凭证待查。 |

在后端 `app/` 下设置测试库的 `AGENT_TEST_DATABASE_URL`，使用本地锁定的 Codex 镜像复跑：

```sh
RUN_CODEX_INSTRUCTION_PROBE=1 .venv/bin/pytest -q tests/test_instruction_runner_db.py tests/test_instruction_runner_codex.py
```

恢复联调用实际 runner 命令入口、Codex WebSocket、HTTPS 控制服务和 PostgreSQL。供给器返回测试容器的位置，供应商为本地合成服务。另在 sunmoon-kind 临时命名空间实测同节点与跨节点的网络策略、回执卷、网关进程重启补交及 PVC/PV 回收，接收方使用合成账单。作者入口、私有冻结和固定图执行的本地验收见下文。目标集群运营路由和真实供应商对账另行验收。

### 作者单轮纯指令试跑与私有冻结

作者在 KnowLab 选择管理中心内本人直接登记的指令版本，或有执行许可的纯指令 Skill，按已声明的输入输出填写用例和断言。每个用例可以重复；每次由宿主发起一个模型轮次，转发器最多放行一次供应商请求。作者提交的断言留在评判端。KnowBench 受理前按总重复次数核对路由报价与整组预算，各次任务分摊预算。受理后若报价已超出该次份额，派发前结束本轮，作者可重新提交预算。

成功回执关联冻结的测试集、来源和定义、每次任务与尝试、线程和轮次、供应商响应编号、用量及根账本核销。断言按各用例的通过次数判定；证据必须逐次齐全。作者可据此冻结并登记私有版本。固定专家图调度见下节。目标集群的运营路由开放另行验收。

在后端 `app/` 用独立 PostgreSQL 运行 `tests/test_formal_instruction_trial_db.py`。同一测试库设置 `RUN_CODEX_INSTRUCTION_PROBE=1` 后，`tests/test_instruction_runner_codex.py` 使用真实 Codex 和本地供应商验证重启及迟到回执。跨服务联调入口是平台仓的 `scripts/local-integration/instruction_author.py`，需要同时提供 `DELIVERY_TEST_DATABASE_URL` 和 `AGENT_TEST_DATABASE_URL`，各指向一次性测试库。传入 `--registered-instruction` 可沿作者来源目录、单方法试跑、两层固定图与三级固定图复跑独立指令的私有冻结。

### 专家引用纯指令的准入与计费基础

KnowBench 可复核作者本人私有登记的精确指令版本。核对项包括来源执行许可、定义与测试集摘要、每次执行的轮次和断言、供应商回执、报价及实际用量。试跑任务清理后从已封存的证据复核；当前安装或执行许可失效时拒绝引用。固定专家可直接引用该版本，也可通过已冻结的私有子专家逐层引用。

新 Attempt 在创建时记录执行资源按 Attempt 分配。网关、工作容器和回执卷归该次执行，额度和实际费用归根 Task。核对费用时，先按 Attempt 找唯一的模型扣款，再对照根账所有扣款的合计。取消后的迟到回执归原 Attempt。试跑清理须等已派发用量核销、执行资源回收。升级前的 Attempt 继续用原任务路径恢复和清理。新版 runner 需要供给器已提供按 Attempt 分配的接口。

### 固定专家图的纯指令步骤

作者为每个固定步骤选定确切方法版本，并在用例中声明输入、输出断言及根预算。运行时按步骤开立 Attempt 和预留费用。每个纯指令步骤单独展示输入字段、前序产物版本、外发目的、供应商、模型、地址和报价上限。用户接受该步后，runner 才能领取专用执行单元。转发器在发送前重读固定输入，核对当前许可证、账号路由、父子授权和批准记录，直接登记的指令另核对批准中的来源身份和版本，授权记录使用 `registered_instruction_id` 和 `registered_instruction_version`。再按已批准的指令正文、业务输入和输出 Schema 构造一次供应商请求。

同一子专家被引用两次时，宿主为每次引用建立独立的调用路径。模型请求发出前，网关核对路径上每层的执行权限、所用子专家在方法技能管理中心的确切登记，以及用户给当前指令步骤的外发批准。中间任一层撤权即停止该次外发。已领取请求的 Attempt 在恢复后继续核销原回执。

结果和用量齐备后，宿主对照输出槽验值。一层图使用 `formal-step:<步骤 ID>`，递归图使用完整路径派生的产物名。子专家按其冻结定义导出结果，下游绑定生产调用、产物 ID、版本、摘要及字段。同名产物产生新版本时仍取原版本。

每步实际费用计入根任务。余额不足以预留下一个步骤的报价时，宿主在发起请求前结束任务并收尾未完成的祖先调用。冻结及后续登记复核会重建字段经过的调用路径，逐项核对批准、产物版本、模型回执和根账费用。

在后端 `app/` 指定独立 PostgreSQL 测试库，运行 `.venv/bin/pytest -q tests/test_formal_instruction_trial_db.py -k fixed`。样例先试跑并私有登记一个纯指令工具，再在专家的两个步骤中分别调用该版本。正常路径验收到专家私有登记，另验用户拒绝、父授权撤销及取消与外发的先后顺序。批准后、领取供应商请求前取消会释放预留；请求已领取时保留未知结果和待核销费用，迟到回执只结算原 Attempt。该组使用合成模型和执行单元。平台仓的 `scripts/local-integration/instruction_author.py` 还会从两个真实服务的 HTTP 路由提交作者用例、逐步批准外发并登记私有专家。

在同一测试环境运行 `tests/test_recursive_instruction_db.py`，覆盖两次调用同一子专家、四次逐步批准、跨子专家的版本交接、中间层撤权、登记变化、恢复与预算不足。上述双服务作者联调也会继续将两步专家用作子专家，试跑并私有冻结三级专家。

### 本人登记的单文件脚本用于正式方法孵化

在方法技能管理中心登记脚本后，作者可在 KnowLab 的「选择已有实现来源」中选定该版本，允许调用来源选宿主。定义须包含输入输出契约、隔离脚本执行权限及验收用例。每次试跑逐步确认来源、参数和报价。脚本从 `arguments.json` 读取输入，将符合声明的输出写入输出目录的 `result.json`。通过试跑后可私有冻结登记，并在固定专家图中按方法版本引用。

KnowBench 在登记簿中按作者、来源 ID、版本和摘要读取脚本。审批和发往执行器前再次核对来源；试跑费用按容器运行时间计入根任务。直接登记脚本的授权独立于安装的 Skill 版本。运行器重启后按原调用取回结果和用量。后续修订保留已经确认的来源版本。

在两套一次性 PostgreSQL 测试库上运行平台仓的 `scripts/local-integration/p1_author.py --registered-script`，沿用该脚本开头的两项数据库配置和 KnowLab 虚拟环境。本地需备好 `luna-local/script-input:work8` 镜像。该用例通过作者接口、P1 编辑组件及真实离线工作容器核验产物，容器时长和价格使用测试配置。后端 `tests/test_formal_script_execution_db.py -k registered_script` 另行覆盖来源修订、摘要重核和三级固定图。

### 固定专家的公开冻结与买方使用

在 KnowBench API 和 runner 的 `WORKBENCH_BUSINESS_COVERAGE_REVIEWS` 配置中提供相同的独立复核记录。每条指定作者主体、方法编号、定义摘要、测试集摘要、证据引用和摘要以及到期时间。直接方法的 `source_digest` 填确切来源指纹，固定专家显式填 `null`。专家定义摘要锁住各步骤的方法编号、版本、摘要及绑定。所有用例通过且唯一有效的复核与本次试跑匹配时，宿主把凭据指纹写入试跑证据。更换凭据需要重新试跑。

作者可在 KnowLab 选择公开冻结。KnowBench 登记时核对根专家实测证据、完整依赖树及同作者各版本的公开交付资格。KnowMart 独立审核上架，获取前重核交付。买方使用普通委托时，需对根专家和实际固定依赖各有使用资格，并选用本人拥有执行许可的连接。双服务验收使用平台仓 `scripts/local-integration/formal_market_delivery.py --expert`，两个测试数据库的设置见该脚本。

## 已接收产物的复核连接与报价

用户在 KnowBench 的模型设置里保存复核连接偏好。只有一个可用连接时可以留空。KnowLab 作者接收一次试跑的步骤产物、选定要交接的输出并通过确定性检查后，可点「去 KnowBench 选复核助手并核对交接范围」。目标应用用自己的登录会话核对作者、原试跑、步骤和产物修订。链接只传定位标识和摘要。

| 部署项 | 如何使用 |
| --- | --- |
| `WORKBENCH_REVIEW_ROUTES` | 按供应商和模型登记规范家族及价目键。用户要求跨家族时，两端都须有已核定且相异的家族。 |
| 沙箱默认供应商、模型、地址 | 本人的有效连接指向这个精确组合时可作为默认候选。限于特定沙箱的连接在本次确认时还须匹配当前沙箱。 |

### 从已确认的交接派发单轮复核

执行单元可使用本人沙箱的默认连接，或向本次网关装载获准的指定连接。作者选择方法技能管理中心中本人登记的一份复核指令及其精确版本，再选择当前沙箱下的空闲项目专家会话。确认发送时显示这次会交出的输出、目的地和单轮上限。`POST /api/workbench/reviews/{run_id}/execution` 只接收交接定位、确认修订、选项摘要、会话和指令版本。平台从已接收的产物重读命名输出。登记的指令正文和这些输出构成该轮业务输入。

已结束的孵化试跑有自己的账本。本次定向复核在所选专家会话内新建委托，以确认金额为根预算。多次提交同一次复核得到同一委托；重开确认页可以进入原会话查看产物。执行器按 Attempt 申请专用执行单元，Codex 在独立的临时工作目录和新线程中运行。网关放行外发前重核 V0、修订、有效账号、价格和目标，按供应商用量回执结算。已发出请求后 runner 重启，读原线程恢复。

供应商、模型、账号和端点必须与已确认选择一致。强制跨家族的定向复核还要核实原产物的实际主笔及本次供应商回报的模型。

### 严格双轮的交接与恢复

作者将自评放在产物的独立命名输出中，确认页分列首轮输出、自评摘要和两轮合计费用上限。用户点「开始严格双轮复核」后，两轮使用同一版本的登记指令、连接和根委托，各有独立的 Attempt、网关、工作容器和线程。

1. 首轮只发送已确认的首轮输出与登记指令。收到匹配的用量回执和非空发现后，运行器在同一数据库事务内保存发现的产物版本、结算首轮并为第二轮预留预算。首轮结果未知时恢复原线程，确认页仍不能交出自评。
2. 第二轮开始及网关即将外发时都重新核对当前复核修订、V0、连接与报价，按首轮 Attempt、产物编号、版本和摘要取回封存的发现。发给第二轮的是原复核指令和对照要求、获准输出、封存发现及指定的作者自评。首次发包和用量回执使用本轮身份。
3. 第二轮失败时，已封存的首轮产物及已用费用留在原委托。成功时，用户可在原项目会话查看两轮产物；确认页重开后可核对首轮发现的版本和摘要。业务分歧由委托人在项目中逐条裁定。

复跑 `tests/test_instruction_runner_codex.py -k strict-review` 使用上述独立库和容器参数。测试分别中断两轮的 runner，在两个隔离容器中恢复各自线程，逐字段检查合成供应商实际收到的请求和根账扣额。

### 裁定复核意见

在 KnowBench 项目的委托列表点「查看复核意见」，也可在原交接确认页查看。委托人从独立复核或对照复核原文摘录意见，逐条选「采纳」「不采纳」或「待定」，填写依据或待补条件后保存。同一条引文按来源产物区分。某轮未完成时，页面列出缺失的报告，只能引用已经封存的部分。保存裁定只追加回执，原试跑的产物、判定及账本继续可查。

### 普通专家图的严格复核与返工

可在一个产出指令与一个复核指令之间声明复核要求。使用 A、B 独立分析及 C 汇合的固定三步草图时，A、B 分别使用独立容器与线程，C 只读各自获准交出的具名结果。选择严格比较时，首轮只拿获准输出，发现封存后再由新容器和线程对照作者自评。选择不同模型家族时，生产环境须配置获准路由、家族映射、账户和有界报价。实际供应商回报的模型必须匹配对应步骤的报价。产出回执无法核实就停止派发复核。工作台在原委托按步骤和角色保留输入版本、实际模型与费用。
